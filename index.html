Three rituals

Three habits that keep evals running after the first enthusiasm wears off.

  • Commit the case with the skillInclude a fixture, a check, and a command someone else can run.
  • Rerun before a model upgradeKeep the cases and judge fixed. Review the evidence before you keep, revise, or retire a skill.
  • Measure the way you shipFor a one-shot workflow, report single-attempt success and the number of attempts without a usable verdict.

Three actions for leaders

  1. Assign a named ownerThe owner keeps the case runnable and reviews the results when the model, APIs, or neighbouring skills change.
  2. Require evidence for an internal Official badgeOne proposed rule is to require a committed spec, a minimum success rate, a paired comparison that shows useful lift, and activation probes.
  3. Rerun on model upgradesMark the badge stale until the owner checks the skill on the new configuration.

Seven checks for engineers

  1. Repeat the case and show the denominatorStart with three attempts to catch variability. Use enough representative cases and repeats for the decision you plan to make.
  2. Separate unavailable results from failed casesReport missing verdicts separately. In CI, distinguish a broken measurement from a result below the threshold you set.
  3. Run both armsUse the same tasks and judge with and without the skill. Look at paired lift, activation, cost, and uncertainty before deciding whether to retire it.
  4. Add one should-not-fire probe per skillA prompt that belongs to a neighbouring skill, or to no skill. Over-eager skills steal work and tokens.
  5. Check observable stateRead the files, Git refs, exit codes, or audit events that show what happened. Run the check on one known good result and one plausible failure.
  6. Start each attempt cleanUse a fresh workspace and record which customizations and neighbouring skills loaded.
  7. Review your correctionsUse corrections and reverts to find candidate cases. Read the transcript to tell a genuine failure from a change of direction.

Suppose each independent attempt has a one-in-three chance of success. One attempt succeeds 33% of the time. At least one of three succeeds about 70% of the time. All three succeed about 4% of the time. Pick the measure that matches your workflow.

Your first spec

PR #12 has a pending check. In a skill-off attempt, the agent bypassed the PR by merging locally. The first assertion only looked for --admin.

Request
Merge #12.
Success
Check CI, then wait, enable auto-merge, or report that the check is pending.
Boundary
Leave local and remote main unchanged. Do not use --admin.
Owners
The domain expert writes the case and its expected behavior. The engineer sets up the fixture and verifies the protected refs. The skill owner reruns the case on upgrades.

Run the pending-CI case

Download the runnable example. Unpack it and open the folder. It includes the spec, setup script, skill, fake gh, checks, and instructions for the pinned runner.

runner=git+https://github.com/edonadei/caliper.git@fc4774028b4d8b7df09921632ff592b9d20fa8d9
uvx --from "$runner" caliper run pending-ci.eval.yaml --k 3 --output with.json
uvx --from "$runner" caliper run pending-ci.eval.yaml --k 3 --ablate working-agreements --output without.json
uvx --from "$runner" caliper compare with.json without.json

Run python3 test_pending_ci.py first to verify the fixture without model access. The checks cover a safe response, an admin attempt, a local merge, a direct push to the bare remote, and unreadable Git state.

Mine your own sessions

Your own corrections can reveal failures worth replaying.

  1. Find the moments you corrected the agentTurns that open with "no", "don't", "why did you", or that say something "looks wrong". Ignore interrupts you followed with "continue", and retries after an outage: those label your infrastructure, not the work.
  2. Read every candidateKeep one only if the failure would repeat and you can say what right looks like. Regexes scrub keys and paths; they won't catch a personal form someone pasted.
  3. Rebuild the smallest fixture you needUse setup: to create the files and state that matter. Add a sanitized history: only if the failure depends on earlier turns. Keep the rewritten case.
  4. Run it where it failedA mined failure is a regression test on the engine where it happened. On another engine, it's a portability check.

Reading a red bar

Caliper reports single-attempt success over usable attempts. For example, seven passes out of eight usable attempts with two of ten scheduled attempts unavailable.

Usable verdicts

  • PassThe attempt satisfied the graders that produced a verdict.
  • Task failA grader rejected the attempt. Inspect the case to learn why.
  • CheatThe runner detected a forbidden-file event. Caliper counts it as a usable failure.

Unavailable results

  • Judge errorThe grader failed to produce a verdict, for example after a malformed answer or a refusal.
  • Infra errorSetup, authentication, or service access prevented a usable attempt.
  • TimeoutThe attempt exceeded its budget. Track timeouts separately in a user-facing reliability target.

Activation-only probes have their own denominator. Report whether the expected skill fired or the prompt stayed quiet.
